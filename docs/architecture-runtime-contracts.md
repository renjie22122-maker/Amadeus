# Runtime behaviour and diagnostics

[简体中文](architecture-runtime-contracts.zh-CN.md)

- **Knowledge → Test retrieval → Search details** shows the trace ID, executed backend, semantic status, and local vector input rows for that query, including empty results. The tool and HTTP endpoint use the same trace; the legacy HTTP response remains an array unless `includeDiagnostics: true` is requested. Local rows read excludes the text/metadata lookup for returned hits. Cached coverage is not an estimate of comparisons inside the external service. A lexical fallback is not evidence that a document is absent.
- Large built-in searches use bounded exact scans. External warm queries can reuse a valid manifest across changes in unrelated scopes. The first query after upgrading may build a new manifest; stored document embeddings are not regenerated by this migration. Eviction, changed authorized vectors, or a change in the eligible set of documents can require a cold read. The UI does not claim that every configured backend ran.
- At a model step, feedback is selected by run; queued user messages are selected by conversation. Delivered history is retained. Scheduled work still reconciles a paused task with a dispatched run. Attachment text previews share 15,000 characters across one delivery batch; unshown text remains accessible using each attachment ID and its own offset. This text allowance does not change the vision budget.
- A workspace heartbeat includes separate revisions for the shell and library. An unchanged view does not trigger a snapshot on each heartbeat; unchanged conditional requests do not rebuild the snapshot. Reconnection still reconciles the active conversation. A stalled stream is disconnected once sustained buffering exceeds the configured high-water guard; reconnects load current state. This is not a guarantee of reconstructing every ephemeral token.
- **Settings → Running service** reports the version recorded in the running build, commit when known, dirty flag and build time. Dev or legacy builds without a manifest report an unknown commit. `/api/health` checks the HTTP lifecycle and a local storage read; it does not run model inference. Authenticated `/api/runtime/status` reports scheduler state and in-process notebook sweep health (not per-chat extraction success). No account data or exception text is included.

Regression fixtures: `tests/architecture-boundaries.test.ts`, `tests/streamed-research.test.ts`, `tests/state-refresh.test.ts`. They use synthetic data; they do not restart or benchmark the live services.

Run `pnpm test:contracts` for synthetic runtime, retrieval, scoped memory and office regressions; `pnpm verify:server` builds and smoke-tests an isolated service without overwriting the live build. These checks do not measure paid model task success.

Browser regression: build the frontend and set `AMADEUS_TEST_REFRESH=1`. Set `AMADEUS_TEST_UI_DIST` if the build is outside `dist`. Run `node --import tsx --test tests/workspace-refresh-browser.test.ts` to check that an unchanged heartbeat issues no state request and a changed library refreshes, using a temporary database and a separate browser.

## Architecture review: coverage and remaining gaps

| Recommendation                           | Implemented behavior and evidence boundary                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Attribute diagnostics to the actual run  | The web conversation and desktop Dot load the run receipt on demand. It shows up to 20 recent ledger requests with first text, first reasoning signal and total duration, the last 20 settled tool durations, the latest memory recall, linked outgoing states and maximum elapsed time from enqueue to platform acknowledgement. Closed panels do not fetch receipts. Legacy samples stay unknown. Timing starts at the model wrapper, not at the network. |
| Deliver the correct delegated result     | Reusing a child conversation does not change which answer a parent receives: waiting selects the specified run's final answer in that conversation, never interrupted output. Concurrency and waiting counts use the root's own descendants and preserve the existing approval and budget policy.                                                                                                                                                           |
| Limit the candidate set before retrieval | Recall and scoped embedding backfill query the SQLite scope index before applying provenance, status and reach checks. A conversation changing memory domain during an embedding request receives no memories from the old domain. Decay, revision and revocation behavior is retained.                                                                                                                                                                     |
| Keep local and bridge boundaries         | Viewing receipts does not call a model or send a message. The response excludes prompts, chat bodies and tool arguments; Dot can inspect only its bound conversation. A platform acknowledgement does not prove the recipient read the message.                                                                                                                                                                                                             |

Not yet measured: real long-running task success, paired cost and quality across providers, and latency distributions after hours idle. Model wrapper latency does not distinguish provider queuing from inference. Synthetic regressions do not answer those questions. Windows isolation readiness remains subject to each backend's own acceptance results.

Reproduce inbox reads and writes with `node --import tsx scripts/inbox-profile.mjs`. It creates in-memory databases, warms both paths and takes 32 samples per case. With 30,000 unrelated rows on Windows and Node 24.20.0, one run measured read p50 of 24.881 → 0.009 ms and p95 of 27.493 → 0.010 ms. Enqueueing and settling 32 rows took 0.408 → 0.511 ms at p50. The index has a write cost; this measures a local SQLite operation, not end-to-end chat latency.
